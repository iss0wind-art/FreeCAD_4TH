## 1. column 미식별 원인 분석

### 수치 요약

| 구분 | B2 (지하 2층) | B1 (지하 1층) | 합계 |

### 원인 1 (주원인, 70~80%): codex 치수 미등재

**핵심 발견**: `지하주차장` source의 codex 7종 단면이 실질적으로 **400×800** 하나만 존재.

```
지하주차장 codex 7종:
  C1, C1A, C2, C2A, C3, C4: 400×800 (6종 — 단면 동일, 기호만 다름)
  C5: 400×900 (1종)
```

전체 codex 91종의 고유 치수(회전 포함): **17가지**만 등재.

`map_instances`의 `dim_match` 함수는 `tol=5mm`이다. 지하주차장 도면에 실제 존재할 것으로 추정되는 기둥 치수들이 codex 17가지에 해당하지 않으면 `candidates=[]`이므로 **즉시 unmatched** 처리된다.

**codex 없는 지하주차장 기둥 표준 치수 예시**:

| 치수 | 설명 | codex 존재 |
|------|------|:------:|
| 500×500 | 정사각형 주차기둥 (가장 흔함) | 없음 |
| 600×600 | 정사각형 주차기둥 (대형) | 없음 |
| 550×550 | 정사각형 주차기둥 (중형) | 없음 |
| 500×800 | 중형 직사각형 | 없음 |
| 500×900 | 중형 직사각형 | 없음 |
| 600×700 | 직사각형 변형 | 없음 |
| 400×600 | 소형 직사각형 | 없음 |

한국 RC 지하주차장에서 가장 흔한 **정사각형 기둥이 codex에 전혀 없다**는 것이 결정적 문제.

### 원인 2 (부원인, 10~20%): source_hint 필터 차단

`map_instances` 로직:
```python
candidates = [c for c in codex if _dim_match(bw, bh, c, tol)]  # 치수 매칭
with_source = [c for c in candidates if _source_match('지하주차장', c)]
```

TC* 계열(101~112동 source) 치수(600×1200, 600×1500 등)는 `dim_match`는 통과하나 `_source_match`에서 걸러진다. 이후 `with_source=[]`이면 `pool=candidates(전체)`로 fallback되어 TC* 매칭은 **가능하지만** confidence가 0.5로 낮아진다.

매칭된 289건 중 TC* 계열이 다수 포함된 것(TC1: 23건, TC2: 20건 등)은 이 fallback이 작동한 결과다. 그러나 이 fallback이 없었다면 미식별 수는 더 많았을 것.

### 원인 3 (B1 특이): wall_pair zone 강등 과다

B1의 `wall_pairs=4459` (B2의 **4배**). `is_in_wall_zone()` 강등이 B1에서 훨씬 많이 발생한다. B1은 B2보다 벽체 구조가 훨씬 복잡한 층 (계단실, 코어 등)이므로 column 후보가 wall_segment로 강등되는 비율이 높다.

B1: 453 박스 → 144 column + 309 wall_segment (67.8%가 벽 강등)  
B2: 476 박스 → 412 column + 64 wall_segment (13.4%가 벽 강등)

## 2. girder 미매칭 원인 분석

### 수치 요약

| 구분 | B2 | B1 | 합계 |
|------|---:|---:|-----:|
| wall_pairs 총계 | 1,141 | 4,459 | 5,600 |
| 거더 codex 매칭 | 2 | 9 | **11** |
| 매칭된 심볼 | RB20 | RB20 | RB20만 |
| 매칭된 두께 | 400mm | 400mm | 400mm만 |

**거더 codex 40종 두께 분포**: 400·500·600·700·800·900·1000mm

**결론**: 거더 codex 자체는 충분하다. 문제는 추출 파이프라인이다.

### 원인 1 (주원인, 90%+): wall_pair 추출의 두께 정밀도 한계

매칭된 11건이 **모두 400mm(RB20)** — 이것이 핵심 증거다.

`run_adapter_2`는 LINE 쌍 간격으로 wall_pair를 생성한다. 두 LINE이 500mm 이상 떨어진 경우 페어링 허용 범위를 초과하거나, 두 LINE 사이에 다른 LINE이 끼어들어 페어링이 실패한다. 500~800mm 두께의 거더 LINE 쌍이 wall_pair로 생성되지 않는 것으로 추정된다.

400mm는 경계값이라 간신히 통과한 것으로 보인다.

### 원인 2 (부원인): is_along_grid 격자 정합 조건

```python
is_along_grid(cl_p1, cl_p2, grid_x, grid_y,
              tol=200.0, axis_angle_tol=0.05)
```

- `axis_angle_tol=0.05rad` ≈ 2.9도: 사선이 조금이라도 기울어지면 탈락
- `tol=200mm`: 격자 중심에서 200mm 이상 떨어지면 탈락
- TEXT 기반 격자 좌표와 wall_pair 중심선 위치 사이의 offset이 200mm 초과 가능

B2 grid_x=16, grid_y=23으로 격자는 충분하지만, wall_pair 중심선이 격자에서 벗어나는 경우가 많을 수 있다.

### 원인 3 (구조적): 파이프라인 근본 한계

지하주차장 거더의 정확한 정보는 **보 리스트 도면(S40-151~156)**에 있다. 현재 `codex_beams_basement.json` 40종의 `pos` 좌표가 보 리스트 도면의 좌표계이므로, 이를 평면도 좌표계로 변환하는 매핑이 구현되면 거더 검출 정확도가 대폭 향상될 것이다.

## 4. 다음 PoC 매칭률 향상 방안

### 단기 (다음 세션 즉시)

**[P1] 지하주차장 기둥 리스트 도면 codex 채굴**

S40 계열 도면에서 전용 기둥 치수를 추출하여 `codex_columns_unified.json`에 추가. 예상 효과: column 매칭률 52% → **80%+**.

**[P2] label_match 활성화**

현재 PoC는 `label=None` 강제. TEXT 레이어에서 `C*`, `TC*` 라벨을 박스에 귀속시키면 `confidence=1.0` 라벨 매칭 가능. 예상 효과: 매칭 신뢰도 전반 향상.

**[P3] source_hint 다중 허용**

`source_hint`를 단일 문자열 대신 리스트로 받아 `['지하주차장', '101~112동']` 동시 허용. 지하주차장에 TC* 계열 기둥이 있는 경우 커버.

### 중기 (다음 세션 이후)

## 시행착오 박제 (실패도 재산)

### 실패 1: source_hint 필터가 만병통치약이 아님

`source_hint='지하주차장'`을 설정했으나 지하주차장 codex 단면이 400×800/400×900 두 가지뿐이라 대부분의 TC* 계열 기둥이 `with_source=[]`로 빠져 fallback 처리됨. source_hint만으로는 부족하며 **치수 등재가 선행조건**이다.

### 실패 2: 거더 wall_pair 추출의 두께 상한 가정이 틀림

`GIRDER_THICKNESS=(400, 850)` 범위를 설정했으나 실제 wall_pairs에서 400mm짜리만 생성되었음. `run_adapter_2`의 LINE 페어링 허용 거리가 500mm 이상을 커버하지 못하는 것으로 추정. 두께 범위 확장이 아니라 페어링 알고리즘 개선이 필요.

### 실패 3: grid=None 설정으로 격자 매칭 비활성

PoC에서 `classify_batch(batch_input, grid=None)`으로 격자 없이 분류. 격자 없으면 column confidence가 0.6으로 낮게 설정. 격자를 TEXT 기반으로 구축했음에도 박스 분류기에 전달하지 않아 격자 교차점 정합 추가 신뢰도 향상을 놓침.
